SAFERIDE — COMPLETE LIVE MONITORING FEATURE REQUIREMENTS

Upgrade the existing Active Journey / SafeRide Monitoring screen into a complete real-time safety monitoring dashboard.

IMPORTANT ARCHITECTURE RULE:

After the user starts SafeRide:

• ALL route information is handled by the Android frontend.
• The selected route, route geometry, distance, ETA, route progress and current position come from the frontend/map/routing system.
• NEVER request or receive a journey/route from Spring Boot.
• Spring Boot must NOT calculate or provide the journey route.
• The backend is used only for SafeRide monitoring/safety processing, persistence and synchronization.
• Only the currently implemented THREE safety algorithms should run in the backend.
• Those three algorithms are currently RULE-BASED and must remain simple/configurable for now.
• Do not replace them with ML or final algorithms yet.
• Do not invent additional backend algorithms.

==================================================
LIVE MONITORING SCREEN
==================================================

After START SAFERIDE, show a complete monitoring dashboard containing:

1. Live journey map
2. Current GPS location
3. Planned route
4. Destination
5. Route progress
6. Distance travelled
7. Distance remaining
8. ETA
9. Elapsed journey time
10. Current journey status
11. Overall safety/emergency score
12. Current risk level
13. Individual safety contributors
14. Live monitoring events
15. Emergency/SOS control
16. Manual testing controls for every safety contributor
17. End SafeRide control

The map remains the main visual element.

==================================================
ROUTE INFORMATION
==================================================

The frontend owns all journey/route information.

Display:

• selected route
• route geometry
• current GPS position
• destination
• route progress
• travelled distance
• remaining distance
• ETA
• elapsed time

The route must NOT come from the backend.

The backend must only receive relevant monitoring information after the frontend has already obtained the route.

Do not hard-code the weights throughout the application.

==================================================
SAFETY CONTRIBUTORS
==================================================

The monitoring screen must expose ALL parameters that contribute to the emergency/safety score.

Include the currently identified safety contributors:

• Route deviation
• Stationary/prolonged stationary condition
• Street-lighting condition
• CCTV/security coverage
• Traffic condition
• Crime/risk level of the area
• Road/environmental safety condition
• Time/context of journey
• Overall location/environment risk

Each contributor must have:

• current value/state
• contribution to safety/risk
• status indicator
• ability to be included in the overall score

Do not hide these factors behind the final score.

The user must be able to see WHY the current safety score changed.

==================================================
THREE CURRENT BACKEND ALGORITHMS
==================================================

Only THREE algorithms are currently active in the backend.

They are RULE-BASED temporary implementations.

Use the currently agreed temporary rules/weights.

For example, if a factor currently has a value/weight such as:

Street lighting = 0
Route deviation = 0.5

preserve the configured values rather than replacing them with invented ML predictions.

The architecture must make it obvious that these are TEMPORARY RULE-BASED VALUES and can later be replaced by the actual algorithms.

Do not claim that these temporary rules are the final SafeRide algorithms.

==================================================

Add a dedicated testing/control section that allows the developer/user to MANUALLY TRIGGER EACH SAFETY CONTRIBUTOR CONDITION.

Provide controls for every contributor.

Examples:

[ Test Route Deviation ]

[ Test Prolonged Stationary ]

[ Test Low/No CCTV ]

[ Test Heavy Traffic ]

[ Test High Area Risk ]

[ Test Unsafe Road/Environment ]

The purpose is to verify:

↓
contributor changes
↓
score changes
↓
risk level changes
↓
monitoring event
↓
appropriate alert

These controls must NOT require changing source code each time.
